# Speckit SSOT

## Purpose

Maintain a domain-level single source of truth (SSOT) as new feature artifacts are generated by Spec Kit commands.

## Trigger Moments

Run this skill after:
- `/speckit.specify`
- `/speckit.plan`
- `/speckit.tasks`
- Any manual edit that creates overlap between feature folders

## Core Principle

Feature folders are temporary production units.
Domain folders are permanent knowledge units.

## Workflow

1. Detect changed/new feature artifacts:
   - Read `.specify/feature.json` when available
   - Compare latest feature folder to existing domain folders
2. Classify content by domain:
   - Map each requirement, scenario, and entity to one bounded context
   - Flag cross-domain items explicitly
3. Merge into domain SSOT files:
   - Merge into `specs/domains/<domain>/spec.md`
   - Merge into `specs/domains/<domain>/plan.md`
   - Merge into `specs/domains/<domain>/data-model.md`
   - Append/refresh contracts in `specs/domains/<domain>/contracts/`
4. Preserve traceability:
   - Update `migration-index.md` with source-to-target mappings
   - Maintain requirement IDs and source references
5. Resolve conflicts:
   - Keep stricter constraint when requirements differ
   - Keep latest accepted clarification when semantics match
   - If conflict is unresolved, create a blocking decision note in `adr/`
6. Minimize duplication:
   - Replace duplicated text with canonical references
   - Keep one normative definition per concept
7. Optional archival:
   - Move old feature folders to `specs/archive/features/` only after successful merge validation

## Default Structure

```text
specs/
├── domains/
│   ├── <domain>/
│   │   ├── spec.md
│   │   ├── plan.md
│   │   ├── data-model.md
│   │   ├── contracts/
│   │   ├── adr/
│   │   ├── migration-index.md
│   │   └── tasks.md
│   └── domain-map.md
└── archive/
    └── features/
```

## Merge Rules

- `spec.md`: business behavior only, no implementation details.
- `plan.md`: implementation decisions and sequencing for the domain.
- `data-model.md`: canonical entities, invariants, and relationships.
- `contracts/`: external interaction contracts only.
- `tasks.md`: executable backlog aligned with the domain SSOT.

If a source section has no clear destination:
- Add to `domain-map.md` under "Unassigned Items"
- Raise at most 5 targeted clarification questions

## Validation Checklist

Before completion, verify:
- No requirement is lost from source feature artifacts
- No domain file contains contradictory requirements
- Domain files remain human-readable and onboarding-friendly
- All merged sections keep provenance references
- New tasks align to merged domain scope

## Output Contract

Return:
1. Domains updated
2. Files created/updated/moved
3. Conflict decisions made
4. Unresolved ambiguities
5. Recommended next command (if any)

## Guardrails

- Never silently drop source content.
- Never merge unrelated domains to reduce file count.
- Prefer incremental merges to large one-shot rewrites.
- Keep terminology consistent with ubiquitous language.
