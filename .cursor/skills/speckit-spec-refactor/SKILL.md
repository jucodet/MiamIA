# Spec Refactor

## Purpose

Maintain a domain-level single source of truth (SSOT) as new feature artifacts are generated by Spec Kit commands.
This skill only runs after domain topology has been created by `speckit-design`.
It also maintains per-domain `review-guide.md` files so reviewers can validate **structure**, **coherence**, and **conciseness** without re-deriving navigation from raw specs each time.

## Trigger Moments

Run this skill after:
- `/speckit.specify`
- `/speckit.plan`
- `/speckit.tasks`
- Any manual edit that creates overlap between feature folders

## Core Principle

Feature folders are temporary production units.
Domain folders are permanent knowledge units.

## Workflow

1. Prerequisite gate (mandatory, blocking):
   - Verify `specs/domains/` exists and contains at least one domain folder with `spec.md`.
   - Verify this structure has been initialized by `speckit-design` (domain folders + per-domain `spec.md`).
   - If not satisfied, refuse to run and return this explicit error:
     - `SSOT refused: domain structure missing. Run /speckit-design first to create specs/domains/<domain>/spec.md.`
2. Build source corpus from all specs:
   - Recursively scan all subdirectories under `specs/`.
   - Include `spec.md` from feature folders only.
   - Exclude all domain outputs from inputs: `specs/domains/**/spec.md`.
   - Exclude generated/archive targets to avoid reinjection loops: `specs/archive/**`.
   - If no eligible feature `spec.md` is found, refuse to run and return this explicit error:
     - `SSOT refused: no feature specs found under specs/**. Create or generate at least one feature spec.md before running /speckit-spec-refactor.`
3. Reconstruct domain specifications:
   - For each existing domain under `specs/domains/<domain>/`, recreate `spec.md` from the complete feature corpus only.
   - Preserve bounded context boundaries defined by `speckit-design`.
   - Merge requirements/scenarios/entities into the right domain; flag cross-domain items explicitly.
   - Treat `specs/domains/<domain>/spec.md` as output-only artifacts for this run.
4. Merge complementary artifacts (optional but recommended):
   - Merge into `specs/domains/<domain>/plan.md`
   - Merge into `specs/domains/<domain>/data-model.md`
   - Append/refresh contracts in `specs/domains/<domain>/contracts/`
5. Preserve traceability:
   - Update `migration-index.md` with source-to-target mappings
   - Maintain requirement IDs and source references
6. Resolve conflicts:
   - Keep stricter constraint when requirements differ
   - Keep latest accepted clarification when semantics match
   - If conflict is unresolved, create a blocking decision note in `adr/`
7. Minimize duplication:
   - Replace duplicated text with canonical references
   - Keep one normative definition per concept
8. Generate reviewer-oriented documentation (mandatory each run):
   - For every `specs/domains/<domain>/` touched, create or refresh `review-guide.md` next to `spec.md`.
   - Purpose: give reviewers a **fast navigation map** and **quality bar** for domain specs — not duplicate normative content from `spec.md`.
   - `review-guide.md` is **meta-documentation only**; all behavioral truth stays in `spec.md`, `plan.md`, `data-model.md`, and `contracts/`.
9. Optional archival:
   - Move old feature folders to `specs/archive/features/` only after successful merge validation

## Review guide contract (`review-guide.md`)

Each domain guide MUST be **short** (target: roughly one screen on a laptop; expand only if multiple bounded contexts warrant subsections).

Required sections (use these headings or equivalent):

1. **À relire en premier** — ordered list of files with one-line purpose each (`spec.md` first, then `data-model.md`, `plan.md`, `contracts/` as applicable).
2. **Périmètre du domaine** — one tight paragraph: in-scope outcomes, explicit **hors périmètre** / délégation aux autres domaines (pointer vers `domain-map.md` si besoin).
3. **Critères de cohérence** — bullet checklist the reviewer uses to confirm no contradiction across artifacts (terminology, entities, flows vs scenarios).
4. **Critères de concision** — bullets: forbidden patterns (e.g. duplicated requirements, orphan IDs, narrative sans critère vérifiable), plus “une phrase = une intention vérifiable” where relevant.
5. **Cartographie des IDs / traçabilité** — how requirement or scenario IDs are formed in this domain, where to find provenance (`migration-index.md`, features sources).
6. **Points de friction habituels** — at most 5 bullets: cross-domain boundaries, naming drift risks, or zones often under-specified.

Style rules for `review-guide.md`:

- Prefer bullets and tables over prose; **no copy-paste** of long excerpts from `spec.md`.
- Link paths relative to the domain folder (e.g. `./spec.md`, `./contracts/foo.md`).
- If nothing friction-worthy exists, write explicitly “Aucun point de friction identifié cette passe.”

## Default Structure

```text
specs/
├── domains/
│   ├── <domain>/
│   │   ├── spec.md
│   │   ├── review-guide.md
│   │   ├── plan.md
│   │   ├── data-model.md
│   │   ├── contracts/
│   │   ├── adr/
│   │   ├── migration-index.md
│   │   └── tasks.md
│   └── domain-map.md
└── archive/
    └── features/
```

## Merge Rules

- `spec.md`: business behavior only, no implementation details.
- `review-guide.md`: reviewer navigation and quality bar only; never normative requirements.
- `plan.md`: implementation decisions and sequencing for the domain.
- `data-model.md`: canonical entities, invariants, and relationships.
- `contracts/`: external interaction contracts only.
- `tasks.md`: executable backlog aligned with the domain SSOT.

If a source section has no clear destination:
- Add to `domain-map.md` under "Unassigned Items"
- Raise at most 5 targeted clarification questions

## Validation Checklist

Before completion, verify:
- Prerequisite gate passed (domain structure from `speckit-design` exists)
- All eligible feature `spec.md` files under `specs/**` were considered as source input
- No `specs/domains/**/spec.md` file was used as source input
- Source corpus is non-empty (at least one eligible feature `spec.md`)
- No requirement is lost from source feature artifacts
- No domain file contains contradictory requirements
- Domain files remain human-readable and onboarding-friendly
- Each updated domain has an up-to-date `review-guide.md` satisfying the review guide contract
- All merged sections keep provenance references
- New tasks align to merged domain scope

## Output Contract

Return:
1. Domains updated
2. Files created/updated/moved (including `review-guide.md` per touched domain)
3. Conflict decisions made
4. Unresolved ambiguities
5. Recommended next command (if any)

## Guardrails

- Refuse execution if `speckit-design` domain structure is missing.
- Refuse execution if no eligible feature `spec.md` exists.
- Never silently drop source content.
- Never merge unrelated domains to reduce file count.
- Prefer incremental merges to large one-shot rewrites.
- Keep terminology consistent with ubiquitous language.
- Never substitute `review-guide.md` for reading `spec.md`; guides compress navigation, not substance.
